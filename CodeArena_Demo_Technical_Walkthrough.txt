CodeArena Demo Technical Walkthrough
====================================

Purpose
-------
This file explains CodeArena from the first login screen to problem execution,
the judge system, and the other major parts of the project. You can use it as
demo speaking notes and as a technical explanation of how the application was
implemented.


1. Overall Architecture
-----------------------
CodeArena is a local Java desktop application. It is built with Java 17,
JavaFX 21, Maven, and SQLite. It does not use a web server, REST API, Spring
Boot, HTML, or a browser-based frontend.

The code is divided into packages:

com.codearena
    Contains MainApp.java, the JavaFX application entry point.

com.codearena.ui
    Contains ScreenFactory.java. This is where the JavaFX screens are created:
    login, register, dashboard, problem list, code editor, profile, battles,
    squad, leaderboard, admin panel, dialogs, charts, tables, and theme logic.

com.codearena.service
    Contains the business logic. Services sit between the UI and database
    layer. For example, AuthService handles login/register logic, ProblemService
    handles problem filtering, JudgeService runs the judge asynchronously, and
    AdminService handles admin operations.

com.codearena.dao
    Contains the data access layer. DAO classes execute SQL queries against the
    SQLite database. For example, UserDAO reads/writes users, ProblemDAO handles
    problems, SubmissionDAO handles submissions, and TestCaseDAO handles test
    cases.

com.codearena.model
    Contains simple Java model classes that represent domain objects such as
    User, Problem, Submission, TestCase, Battle, Badge, and Squad.

com.codearena.judge
    Contains the local judge system. JudgeEngine controls the judging process,
    TestCaseRunner executes one test case, Sandbox creates/deletes temporary
    code folders, PythonRuntime locates Python, and Verdict represents AC, WA,
    CE, RE, and TLE.

com.codearena.util
    Contains helper classes such as DBConnection, SchemaInitializer,
    SeedInitializer, PersistenceHandler, SessionManager, NavigationUtil,
    XPCalculator, and custom exception classes.

The main layered flow is:

UI screen -> Service class -> DAO class -> SQLite database

For submissions, the flow becomes:

Code editor UI -> JudgeService -> JudgeEngine -> Sandbox/TestCaseRunner
              -> SubmissionDAO/UserProgressService/BadgeService


2. Application Startup
----------------------
The application starts from:

    src/main/java/com/codearena/MainApp.java

MainApp extends javafx.application.Application. JavaFX calls the start(Stage)
method when the program launches.

MainApp does these things:

1. Calls PersistenceHandler.initialize().
2. Creates the first Scene using ScreenFactory.create("login").
3. Sets the window title to CodeArena.
4. Sets minimum window size.
5. Loads the application icon from /images/logo-mark.png.
6. Shows the startup splash screen.
7. When the application closes, stop() calls PersistenceHandler.shutdown().

PersistenceHandler is responsible for preparing the database. It uses:

    DBConnection
    SchemaInitializer
    SeedInitializer

DBConnection opens the SQLite database. By default, the database is:

    data/codearena.db

SchemaInitializer reads:

    src/main/resources/data/schema.sql

and creates missing tables.

SeedInitializer reads:

    src/main/resources/data/seed.sql

and inserts demo users, problems, test cases, badges, and other seed content.

This means a fresh install can recreate the database structure from the schema
and seed resources.


3. Login Flow
-------------
The login screen is created in:

    ScreenFactory.login()

Main classes involved:

    ScreenFactory
    AuthService
    UserDAO
    SessionManager
    NavigationUtil
    User

How it works:

1. ScreenFactory.login() builds the JavaFX controls:
   username field, password field, login button, register link, guest problem
   browsing button, public leaderboard button, and theme toggle.

2. When the user clicks Login, the UI calls:

       AuthService.login(username, password)

3. AuthService checks:
   - username is not blank
   - password is not blank
   - user exists
   - password matches the stored BCrypt hash
   - account is active

4. AuthService uses UserDAO.findByUsername(username) to load the user from
   SQLite.

5. Password verification is done with:

       BCrypt.checkpw(password, user.getPassword())

6. If the login is successful, ScreenFactory stores the user with:

       SessionManager.setCurrentUser(user)

7. Then the UI checks the role:
   - ADMIN users go to the admin panel.
   - CODER users go to the coder dashboard.

8. Navigation is done through:

       NavigationUtil.navigateTo("dashboard", button)
       NavigationUtil.navigateTo("admin-panel", button)

SessionManager is important because it keeps track of who is currently logged
in. Many screens check SessionManager.isLoggedIn() before allowing access.


4. Registration Flow
--------------------
The register screen is created in:

    ScreenFactory.register()

Main classes involved:

    ScreenFactory
    AuthService
    UserDAO
    User
    BCrypt

How it works:

1. User enters username, email, and password.
2. ScreenFactory calls AuthService.register().
3. AuthService validates:
   - username is required
   - email is required
   - password is required
   - password length must be at least 8 characters
   - username must not already exist
4. Password is hashed with:

       BCrypt.hashpw(password, BCrypt.gensalt())

5. A User object is created with role CODER.
6. UserDAO.register(user) inserts the user into SQLite.

This keeps password storage safer because plain passwords are not stored in the
database.

8. Code Editor and Submission Creation
--------------------------------------
The code editor screen is created in:

    ScreenFactory.codeEditor()

Main classes involved:

    ScreenFactory
    JudgeService
    ProblemService
    UserProgressService
    BadgeService
    Submission
    SessionManager

The editor screen lets the user:

    choose Java or Python
    write code
    run sample tests
    submit against all tests
    see verdict and detailed test output

ScreenFactory stores code templates:

    TEMPLATE          Java starter code
    PYTHON_TEMPLATE   Python starter code

When the user changes language, the editor template changes.

When the user clicks Run or Submit, ScreenFactory calls runJudge().

runJudge() does this:

1. Checks that a problem is selected.
2. Checks that a user is logged in.
3. Creates a Submission object using buildSubmission().
4. Sets:
   - userId
   - problemId
   - source code
   - language
5. Calls JudgeService.evaluateReportAsync().

There are two modes:

Run:
    sampleOnly = true
    Uses only sample test cases.
    Does not permanently save the submission as a real attempt.

Submit:
    sampleOnly = false
    Uses all test cases.
    Saves the submission and updates progress if accepted.


9. JudgeService: Keeping the UI Responsive
------------------------------------------
JudgeService is located at:

    src/main/java/com/codearena/service/JudgeService.java

Main classes involved:

    JudgeService
    JudgeEngine
    javafx.concurrent.Task
    Platform.runLater()

JudgeService exists because judging code can take time. If judging ran directly
on the JavaFX UI thread, the whole application could freeze.

JudgeService creates a JavaFX Task and runs it on a daemon worker thread:

    Thread worker = new Thread(judgeTask, "judge-service-worker")
    worker.setDaemon(true)
    worker.start()

When the judge finishes, JudgeService returns results back to the UI using
Platform.runLater(). This is important because JavaFX UI components should only
be updated on the JavaFX Application Thread.

JudgeService returns a JudgeReport containing:

    final Verdict
    list of TestCaseRunner.TestCaseResult objects

Each test result contains:

    verdict
    input
    actual output
    expected output
    runtime in milliseconds


10. JudgeEngine: Main Judging Process
-------------------------------------
JudgeEngine is located at:

    src/main/java/com/codearena/judge/JudgeEngine.java

Main classes involved:

    JudgeEngine
    TestCaseDAO
    SubmissionDAO
    Sandbox
    TestCaseRunner
    PythonRuntime
    Verdict

JudgeEngine.runSubmission(submission, sampleOnly) is the main judge method.

Step by step:

1. Save or prepare the submission.

   For full submissions, if the submission has no id yet, SubmissionDAO saves
   it first. For sample-only runs, JudgeEngine creates a temporary id.

2. Normalize the language.

   If the language is Python, it stays Python. Otherwise, it defaults to Java.

3. Create a temporary sandbox folder.

   Sandbox.createTempDir(submissionId) creates a folder under the OS temp
   directory:

       temp/codearena/{submissionId}

4. Write the source code file.

   Java source is written as:

       Solution.java

   Python source is written as:

       solution.py

5. Compile or check syntax.

   Java:
       javac Solution.java

   Python:
       python -m py_compile solution.py

   PythonRuntime checks possible Python commands:

       python
       python3
       py -3

6. If compilation fails, verdict becomes CE.

7. Load test cases.

   sampleOnly = true:
       TestCaseDAO.getSampleByProblemId(problemId)

   sampleOnly = false:
       TestCaseDAO.getByProblemId(problemId)

8. Run every test case using TestCaseRunner.run().

9. Choose the final verdict.

   JudgeEngine starts with AC. If a test returns WA, RE, TLE, or CE, it updates
   the overall verdict based on Verdict.priority().

10. Stop early on terminal verdicts.

    Some verdicts are terminal, so the judge can stop running more tests.

11. Save final verdict and runtime for full submissions.

12. Always clean the sandbox in the finally block.

This cleanup is important because user source files and compiled class files
should not remain in the temp directory.


11. TestCaseRunner: Running One Test Case
-----------------------------------------
TestCaseRunner is located at:

    src/main/java/com/codearena/judge/TestCaseRunner.java

Main classes involved:

    TestCaseRunner
    ProcessBuilder
    TestCase
    Verdict

TestCaseRunner.run(testCase, workingDir, language) executes one compiled
program against one input.

How it works:

1. Builds the run command.

   Java:
       java -cp . Solution

   Python:
       python solution.py

2. Starts the process using ProcessBuilder.

3. Writes the test case input to the process stdin.

4. Reads stdout and stderr using separate reader threads.

5. Waits up to 5 seconds.

6. If the program does not finish in time:

       process.destroyForcibly()
       verdict = TLE

7. If the process exits with a non-zero exit code:

       verdict = RE

8. If the process exits normally:

       actual output is compared with expected output

9. Output comparison normalizes line endings and trims whitespace:

       \r\n and \r become \n
       leading/trailing whitespace is ignored

10. If normalized output matches expected output:

       verdict = AC

    Otherwise:

       verdict = WA


12. Verdict System
------------------
Verdict is an enum in:

    src/main/java/com/codearena/judge/Verdict.java

Main verdicts:

AC
    Accepted. Output matches expected output.

WA
    Wrong Answer. Program ran, but output was incorrect.

CE
    Compilation Error. Java compilation or Python syntax check failed.

RE
    Runtime Error. Program crashed or judge hit an execution exception.

TLE
    Time Limit Exceeded. Program ran longer than allowed.

Verdict also stores:

    priority
    display name
    display color
    terminal status

Priority helps JudgeEngine decide which verdict should become the final verdict
when multiple test cases are involved.

14. Progress, XP, Rank, and Streaks
-----------------------------------
Progress is handled mainly by:

    UserProgressService
    XPCalculator
    UserDAO
    SessionManager

When a user submits a full solution and gets AC, ScreenFactory checks whether
the problem was already solved:

    ProblemService.isSolvedByUser(problemId, userId)

If it was not already solved, ScreenFactory calls:

    UserProgressService.awardProblemSolved(user, problemId, difficulty, alreadySolved)

UserProgressService then:

1. Adds XP based on difficulty.
2. Increments problems solved.
3. Updates streak days.
4. Calculates rank title using XPCalculator.
5. Saves progress with UserDAO.updateProgress().
6. Refreshes the current session user.

For battle wins, UserProgressService.awardBattleWin() updates:

    winner XP
    winner rank
    winner battle wins
    loser battle losses

The updated user is loaded again from the database so the UI can show fresh
data.

18. Battle System
-----------------
Battle logic is handled by:

    BattleService
    BattleDAO
    UserDAO
    ProblemDAO
    UserProgressService
    JudgeService

Battle screens are created in ScreenFactory:

    battleLobby()
    battleOneVsOne()
    battleFreeForAll()
    battleRandomOneVsOne()
    battleArena()

Supported battle modes:

ONE_V_ONE
    A direct two-player battle.

FREE_FOR_ALL
    Multiple players join the same room.

RANDOM_ONE_V_ONE
    The app tries to match a user with another waiting player.

Battle flow:

1. User chooses battle mode and difficulty.
2. BattleService selects a random published problem with matching difficulty.
3. A Battle object is created and saved.
4. For room-based battles, BattleService creates a join code.
5. Another player joins using the join code.
6. Players become battle participants.
7. When ready, battle status becomes ACTIVE.
8. The battle arena opens with the selected problem and timer.
9. The user submits code through the same JudgeService/JudgeEngine system.
10. If a participant gets AC, BattleService.finishWithWinner() can finish the
    battle.
11. UserProgressService awards battle XP and updates win/loss stats.
12. If time expires, BattleService.finishAsDraw() marks the battle as DRAW.

The battle system reuses the normal judge system instead of having a separate
judge. That keeps problem solving behavior consistent across normal practice
and battle mode.


19. Squad System
----------------
Squads are handled by:

    SquadService
    SquadDAO
    UserDAO
    Squad
    User

The squad screen is created in:

    ScreenFactory.squad()

Squad features:

    create a squad
    join a squad by name
    view squad members
    remove members if leader
    view squad leaderboard
    calculate combined squad XP

SquadService rules:

1. A user must be logged in.
2. A user cannot create a squad if already in a squad.
3. Squad name is required.
4. Squad name must be unique.
5. Only a squad leader can remove members.
6. A leader cannot remove themselves through removeMember().

The user table stores squad_id, which connects a user to a squad.

22. Database Design
-------------------
The database schema is in:

    src/main/resources/data/schema.sql

Main tables:

users
    Stores accounts, password hashes, role, XP, rank, solved count, battle
    stats, streak, active status, and squad id.

problems
    Stores problem statement, difficulty, category, tags, constraints, input
    format, output format, time limit, memory limit, publish status, and creator.

test_cases
    Stores input, expected output, sample/hidden flag, and order for each
    problem.

submissions
    Stores submitted source code, language, verdict, runtime, user id,
    problem id, battle id, and submission time.

battles
    Stores player ids, problem id, winner id, join code, battle mode, status,
    start/finish time, and time limit.

battle_participants
    Stores users who joined battle rooms and whether they are ready.

badges
    Stores badge definitions and image paths.

user_badges
    Stores earned badges for users.

squads
    Stores squad name, description, leader id, and created time.

DBConnection enables SQLite foreign keys with:

    PRAGMA foreign_keys = ON

This helps maintain relationship integrity.

28. Short Explanation for Viva
------------------------------
CodeArena is built as a layered JavaFX desktop app. The UI is created in
ScreenFactory. When the user logs in, AuthService validates credentials using
UserDAO and BCrypt, then SessionManager stores the current user. The problem
screens use ProblemService and ProblemDAO to load published problems and test
case samples.

When a user writes code, ScreenFactory creates a Submission object and sends it
to JudgeService. JudgeService runs the judge in a background JavaFX Task so the
UI does not freeze. JudgeEngine writes the code into a temporary sandbox folder,
compiles Java or checks Python syntax, loads test cases from SQLite, and asks
TestCaseRunner to execute the program for each input. TestCaseRunner captures
stdout/stderr, applies a time limit, compares output with expected output, and
returns a Verdict. JudgeEngine stores the final verdict and cleans temporary
files.

If the submission is accepted, UserProgressService updates XP, rank, solved
count, streak, and battle stats. BadgeService checks milestones and awards
badges. ProfileService loads submissions, battles, charts, badges, and editable
profile details. AdminService handles users, problems, test cases, and
submissions, while AnalyticsService calculates admin dashboard metrics. All data
is stored in SQLite through DAO classes, and the schema/seed files recreate the
initial database.
